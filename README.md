## 📊 미디어믹스 벤치마크 데이터

`js/data/mediamix-data.js` 한 파일이 **미디어믹스 플래너**와 **매체 벤치마크 ② 업종별 실측표**를
동시에 먹인다. 수치를 갱신할 땐 이 파일의 `rows` 만 갈아끼우면 두 화면에 함께 반영된다.

- 출처: 플레이디 재직 시 제작한 *구글 Ads / Meta Ads 미디어믹스 간편 플래너(2024~2025)* PWA 원본 데이터
- 구글: 업종 19 × 디바이스 2(MO/PC) × 채널 7 = **195행**
- Meta: 업종 17 × 통합 × 목표 7 = **119행**
- 행 형식: `[업종, 디바이스, 채널ID, CPC, CTR(%), CPM, CPV, VTR(%), CPI]` — `null` = 데이터 없음
- **주의**: CPC·CTR·CPM은 각각 따로 평균 낸 값이라 `CPC × CTR × 1000 ≠ CPM` 인 행이 있다.
  플래너는 클릭을 CPC로, 노출을 CPM으로 산출하고 그 차이를 화면에서 안내한다.
- 선택 업종에 데이터가 없으면 **전 업종(통합)** 값으로 자동 대체하고 `통합 대체` 배지를 붙인다.
- 전환·매출(ROAS/CPA/CVR/전환수/매출)은 이 데이터에 **없다.** 플래너에서 `기본 CVR`·`기본 객단가(AOV)`를
  입력해야 전환수·CPA·매출·ROAS가 산출된다(= 우리 계정 과거 실적을 넣는 자리).
- **네이버·카카오·크리테오 등 국내 매체도 없다**(구글·Meta 집행 데이터라서). 실제 믹스에서 비중이 큰
  이 매체들은 플래너의 `[+ 국내 매체]` 버튼으로 행을 추가하고 단가를 직접 넣는다.

### 업종 분류 통합 · 전 업종 대체

구글과 Meta 가 서로 다른 업종 체계를 쓴다(원래 교집합 2개). 그대로 두면 **'패션·잡화'는 구글만,
'이커머스'는 Meta 만** 잡혀 한쪽 플랫폼이 통째로 빠진 믹스가 나왔다. 두 단계로 해결했다.

1. **통합 매핑** — 구글 체계를 기준으로 Meta 업종을 얹는다(`mix-autoplan.js` 의 `aliases`).
   등가가 확실한 것만 매핑하고(이커머스→리테일(종합몰), 게임·엔터→게임·e스포츠, 여행·레저→트래블 …),
   카테고리를 단정할 수 없는 것(일반 소비재·프로서비스)은 **'기타(일반)'로 보낸다.**
   일반 소비재를 뷰티·패션으로 밀면 근거 없는 업종 수치가 만들어지므로 그렇게 하지 않는다.
   → 업종 33개 → 19개, 양 플랫폼이 함께 잡히는 업종 3개 → 11개.

2. **전 업종 대체** — 그래도 비는 상품은 같은 상품의 **전 업종(통합)** 값으로 채우고,
   `sectorFallback` 을 세워 근거·비고·화면 안내에 "전 업종 대체"임을 밝힌다.
   해당 업종 자료가 있으면 대체본은 쓰지 않는다.

### 국내 매체 참고 단가 (`js/data/kr-benchmarks.js`)

MM_DATA 에 없는 네이버·카카오·크리테오의 **출발점 단가**. 2024~2026 집행 미디어믹스 산출물을
상품 단위로 모아 중앙값을 냈다.

- **단가와 CTR 만 담는다.** CVR·객단가·매출은 넣지 않는다 — 전환은 광고주 사업 성과라
  여기 값을 쓰면 근거 없는 매출 추정이 된다. 각자 실적을 플래너에 넣어야 한다.
- **브랜드명·캠페인명은 담지 않는다.** 이 저장소는 공개다. 표본 수와 관측 범위만 note 에 남긴다.
- 업종은 전부 **전 업종(통합)** — 위의 전 업종 대체 규칙으로 모든 업종에 연결된다.
- 표본이 얕은 상품은 `sourceKind` 를 **'가정'** 으로 낮춰 엔진이 뒤로 밀도록 했다
  (근거 등급: 실적 > 과거 제안 > 참고값 > 가정). 현재 참고값 4 / 가정 9.
- 네이버 브랜드검색은 기간 정액이라 **단가를 넣지 않았다**(FIXED). 계약 물량·단가를 직접 넣어야 한다.

### 성과 리포트 붙여넣기

벤치마크 화면에서 지난 캠페인 리포트 표를 **헤더째 복사해 붙여넣으면** 매체를 알아보고 단가를 뽑는다.
파일을 만들 필요 없이 시트에서 바로 긁어오는 경로다.

- `imps·click·spending` 만 있어도 CTR·CPC·CPM 을 역산하고, `order·revenue` 가 있으면 CVR·객단가까지 만든다.
- 상품의 과금 기준에 맞춰 `rate` 를 담는다(CPC 상품이면 CPC, CPM 상품이면 CPM).
- 결과는 파일 가져오기와 **같은 검토 절차**(신규/중복/내용 충돌 확인)를 지나 이 브라우저에만 저장된다.

> ⚠️ 비율 컬럼은 `"1.61%"`(퍼센트)와 `0.0161`(소수)이 섞여 들어온다.
> 값 크기로 판단하면 **CVR 0.18% 같은 진짜 작은 퍼센트를 18%로 부풀린다.** 원본 문자열의 `%` 유무로 구분한다.

### 손익분기 검증

계획에 **마진율**(+건당 기타 변동비)을 넣으면 검수·제출본 화면에서 본전 여부를 판정한다.

```
MixEngine.breakEven(aov, margin, other) → { beCpa, beRoas, unreachable, ... }
  손익분기 CPA  = 객단가 × 마진율/100 − 건당 기타 변동비   (= 건당 공헌이익)
  손익분기 ROAS = 기타 변동비 0 이면 100 ÷ (마진율/100)
                  아니면 객단가 ÷ 공헌이익 × 100 (공헌이익 ≤ 0 → 달성 불가)
```

- 계획 전체를 대표할 객단가가 필요해 **구매 목적 행들의 전환 가중 평균 객단가**를 쓴다.
- 손익분기 공식은 `mix-engine.js` **한 곳에만** 둔다. `budget.js` 의 손익분기 계산기도 이 함수를 호출한다
  (같은 공식을 두 번 구현하면 언젠가 값이 갈라진다).

### 만져도 되는 것과 안 되는 것

- **`gh-pages` 브랜치를 직접 수정하지 않는다.** 다음 미러링에서 강제로 덮어써진다. 항상 `main` 에서 작업한다.
- **Settings → Pages 의 Source 를 바꾸지 않는다.** 현재 `gh-pages` / `/ (root)` 로 서비스 중이다. 여기를 건드리면 사이트가 다시 404 가 될 수 있다.
- 경로는 모두 **상대경로**(`css/base.css` 형태)로 유지한다. `/css/...` 처럼 절대경로로 쓰면 `/pm-hub/` 하위 경로 배포에서 404 가 된다.
- 루트의 `.nojekyll` 을 지우지 않는다. Jekyll 처리를 건너뛰게 하는 파일이다.

### 404 가 날 때 확인 순서 (2026-07 실제 사고 기록)

1. **리포지토리가 공개인지** — 비공개로 바꾸면 무료 플랜에서는 Pages 가 즉시 중단된다.
2. **Pages 가 활성화돼 있는지** — `has_pages` 가 `false` 면 파일이 정상이어도 전체가 404 다.
   ```bash
   curl -s https://api.github.com/repos/vetnam555-del/pm-hub | grep has_pages
   ```
   Settings 화면의 브랜치 소스 저장이 반영되지 않는 일이 있었다. 그때는 `gh-pages` 브랜치를
   푸시하면 Pages 가 자동 활성화된다(이 방법으로 복구했다).
   ```bash
   git push origin main:gh-pages
   ```
3. **Actions 실행 결과** — Actions 탭에서 `Mirror main to gh-pages` 와 `pages build and deployment` 가 모두 성공인지 본다.

> `actions/deploy-pages` 방식은 쓰지 않는다. Actions 토큰에 Pages 생성·설정 권한이 없어
> `Resource not accessible by integration` 으로 실패한다(2026-07-27 확인).
